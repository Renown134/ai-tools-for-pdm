# Карточка кейса «Кто выгуливает Бориса»

Учебный micro-MVP для вымышленной компании «Догяндекс»: общая страница, на которой сотрудники записываются на прогулку с офисным псом Борисом и видят, кто кормил его последним.

## Демо

Видео главного сценария (76 секунд, без звука): дата и пять слотов → запись сотрудника → отказ при попытке занять слот, занятый другим сотрудником во втором браузере → обновление страницы с сохранением записей → отметка кормления → узкий экран:

https://github.com/Renown134/ai-tools-for-pdm/raw/sprint-1/demo/boris-demo-sprint1.webm

## Гипотеза

Если сотрудник видит только пять понятных слотов на сегодня и состояние каждого слота, он может самостоятельно выбрать свободный слот и зафиксировать запись без обращения к администратору.

## Главный сценарий

1. Сотрудник открывает общую страницу и видит текущую дату и пять слотов (09:00–17:00).
2. Выбирает свободный слот, вводит ФИО, подтверждает запись.
3. Слот становится занятым, в нём отображается введённое ФИО.
4. Другой сотрудник при попытке занять тот же слот получает понятный отказ сервера.
5. После обновления страницы или во втором браузере состояние то же (SQLite).

Дополнительная функция: карточка «Последнее кормление» с отметкой нового кормления по ФИО.

## Что построено

- Node.js-сервер без внешних зависимостей (встроенный `node:sqlite`, Node 22.5+): раздача страницы и JSON API (`/api/slots`, `/api/slots/book`, `/api/feedings`, `/api/feedings/latest`).
- Защита от двойной записи — одна атомарная SQL-операция `UPDATE ... WHERE booked_by IS NULL`; конфликт возвращается с кодом 409 и понятным сообщением.
- Одна страница без фреймворков (`public/index.html`): слоты, ввод ФИО, карточка кормления; адаптивная вёрстка.
- Хранение — настоящий SQLite-файл `boris.db` в папке проекта; слоты на текущую дату создаются автоматически.

## След одной ключевой итерации с ИИ: защита от двойной записи

**Какую задачу я дал агенту.** «Добавь запись в слот: сервер изменяет только свободный слот; если запись уже появилась до выполнения запроса — верни понятный конфликт и не перезаписывай первоначальное ФИО; используй одну атомарную операцию, не "прочитал свободен — потом записал"» (этап 3 из `PLAN.md`, требование `spec.md`).

**Что агент сделал.** В `server.js` — маршрут `POST /api/slots/book` с валидацией ФИО (непустое после `trim`), подготовленный `UPDATE walk_slots SET booked_by = ?, booked_at = ? WHERE walk_date = ? AND slot_time = ? AND booked_by IS NULL` — решение о занятости принимает сама SQL-операция; при `changes === 0` сервер возвращает 409 с текстом «Слот … уже занят (ФИО). Выберите другой слот.» и текущим содержимым слота, перезаписи нет.

**Как я проверил результат.** Фактическими запросами к работающему серверу: успешная запись «Анна Тестова» в 09:00; повторная попытка с другим ФИО в тот же слот — ответ 409, в БД и в ответе осталось «Анна Тестова»; пустое ФИО из пробелов — 400; несуществующее время слота — 404. Затем в браузере: страница с устаревшим состоянием при попытке занятия занятого слота показала то же сообщение об отказе, и запись не изменилась.

**Почему принял и что поправил.** Принял, потому что проверка показала именно серверный отказ (не скрытие кнопки), а SQL-решение атомарно по построению — отдельного «чтения перед записью» в коде нет. Поправил по ходу одно место: SELECT после неудачного UPDATE агент оставил только для текста сообщения, и я отдельно проверил, что он не участвует в решении о записи. Итоговая проверка в UI вошла в видео-демо (отказ на 30-й секунде).

Детальная история разработки в git не сохранилась (проект попал в репозиторий одним коммитом), поэтому ключевая итерация описана выше, а статусы и проверки всех этапов зафиксированы в `PLAN.md`.

## Границы

Намеренно не входит: авторизация, роли, отмена записи, календарь на неделю, уведомления, интеграции, деплой, масштабирование. Это учебный micro-MVP, все данные синтетические.
