### Этап 2. Каркас Node.js-проекта и SQLite ✅

Задачи:

- `package.json` с локальным npm-способом запуска (`npm install`, `npm start`).
- Выбор и установка совместимого с Node.js SQLite-драйвера (только необходимая зависимость).
- Настоящий SQLite-файл в папке проекта; таблицы `walk_slots` и `feedings` строго по схеме из `spec.md`.

Проверка: `npm install` и `npm start` проходят без ошибок; файл БД создан; в `walk_slots` ровно пять строк на текущую дату.

DoD: напрямую не закрывает, готовит основу для DoD 5.

### Этап 3. Серверное поведение

Задачи:

- `GET`: текущая дата и состояние пяти слотов.
- `POST` записи в слот: ФИО непустое после удаления лишних пробелов; сервер изменяет только свободный слот одной атомарной операцией; при попытке занять занятый слот — понятный конфликт, первоначальная запись не меняется.
- `GET` / `POST` кормления: последнее кормление (время и ФИО) и отметка нового кормления по ФИО.

Проверка: ручные запросы к серверу — успешная запись; повторная запись в занятый слот возвращает конфликт и не перезаписывает ФИО; пустое ФИО отклоняется.

DoD: 4 (серверная часть), серверная основа для 3 и 5.

### Этап 4. Страница

Задачи:

- Текущая дата и ровно пять фиксированных слотов.
- Свободные и занятые слоты визуально различаются; у занятого видно ФИО и нет действия повторной записи.
- Для свободного слота — ввод ФИО и подтверждение; понятное отображение конфликта от сервера.
- Карточка «Последнее кормление»: время и ФИО; отметка нового кормления с обновлением карточки.
- Читаемость и работоспособность главного сценария на широком и узком экране.

Проверка: главный сценарий из `spec.md` в браузере; обновление страницы; второй браузер.

DoD: 1, 2, 3, 6, 7.

2. ⬜ Запись синтетического сотрудника в свободный слот.
3. ⬜ Повторная запись в тот же слот — проверка отказа.
4. ⬜ Обновление страницы или второй браузер — запись сохранена.
5. ⬜ Отметка кормления синтетическим ФИО и обновление карточки.

## Правила работы (кратко, из `AGENTS.md`)

- Одна явно сформулированная задача за итерацию; решение о принятии изменения — за студентом.
- Постоянное состояние — только SQLite по схеме из `spec.md`, без `localStorage`, моков и состояния в памяти.
- Защита от повторной записи — атомарно на сервере, не только скрытием кнопки.
- Только синтетические данные; без авторизации, отмены записи, календаря на неделю, уведомлений, интеграций и деплоя.
- Commit, push, публикация и удаление данных — только по явному запросу студента.
